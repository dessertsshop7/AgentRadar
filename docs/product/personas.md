# 用户画像与优先级

状态：2026-10-17，P01 产品假设。下列是设计用角色模型，不是访谈对象、真实个人经历或调研结论。
优先级与 [PRD](prd.md) 一致；用户故事编号用于追踪，不在这里重复验收表。

| 维度 | 首要：产品/运营人员 | 次要：AI 初学者 | 后续重点：技术支持人员 |
| --- | --- | --- | --- |
| 目标 | 用合适的工具完成一个工作任务，减少选型和试错时间 | 看懂工具、判断能否上手，完成第一次尝试 | 帮团队部署、排障、维护并沉淀经验 |
| 痛点假设 | 工具介绍只讲技术/热度；不知道是否支持自身流程 | 不理解 README、配置文件、API Key 和依赖 | 错误缺上下文、安装说明过期、处理过程难复用 |
| 技术基础假设 | 会使用 Web 产品与表格，部分能配置可视化工作流 | 会浏览网页，可能未用过 Git/终端 | 能看日志、管理环境与容器，技术范围不完全相同 |
| 典型任务 | 将团队资料整理成可查询知识，或组织内容生产流程 | 搜索“文档整理”，理解一个项目的用途与门槛 | 收集版本/系统/错误信息，按依据诊断并验证解决 |
| 约束 | 时间有限、预算和敏感数据范围要确认；不一定有部署协助 | 设备和权限有限，不能假定能安装运行时 | 需要维护窗口、访问权限、审计和责任边界 |
| 决策因素 | 任务适配、人工投入、费用、输出可核对性 | 中文清晰、步骤可理解、低门槛、失败后有退路 | 版本兼容、来源可信、可重复验证、安全与维护成本 |
| 所需帮助 | 先表达场景/约束，再解释候选与排除原因 | 术语解释、适用/不适用、安装前置检查和未知项 | 结构化环境信息、脱敏日志、知识条目和支持记录 |
| 成功判断 | 实际任务完成且自报结果；点击外链不能算成功 | 能说明工具能做什么、需要什么，完成一次可验证尝试 | 原故障可复现且修复后不再发生，有版本与环境证据 |
| 故事关联 | US01/03/06–08/12–14/17/27/28 | US02/04/09–10/19 | US05/11/15–16/18/21–26 |

## 为什么这样排序

产品/运营的具体任务有助于观察“发现到反馈”闭环，这是选为首要用户的假设依据，不是市场规模结论。
初学者共享目录和解释能力，首版提供可理解的中文与门槛，但不承诺所有工具都无需代码。
技术支持参与早期内容核实和工程检查；完整排障系统与团队工作台需要更多上下文、权限和知识维护，安排在增强/企业版。

## 后续测评方法

- 使用相同任务观察三类用户：找到一个工具、复述适用条件、说明下一步如何试用。
- 记录看到的信息、卡住的步骤、主动退出原因；不把完成原型流程视为真实工具应用成功。
- 分开询问“介绍是否理解”“愿不愿意尝试”“是否实际尝试”“结果是什么”，不使用诱导式成功提问。
- 收集前说明目的与范围；反馈可拒绝；尚未决定任何个人信息、设备指纹或跨设备跟踪方案。
- H01–H06 的待验证问题集中在 PRD；实际访谈和测评记录后续另建并标明来源，不回填虚构故事。
